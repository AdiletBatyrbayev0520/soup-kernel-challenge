# Per-process report: where time and memory go in one training step — base Soup vs `unsloth` branch

Local **RTX 5090** in bf16 (the jury's T4 uses fp16). Task: Qwen2.5-1.5B-Instruct 4-bit NF4,
LoRA r=16 on q/v, batch 4 × 512 tokens, 28 layers, vocab 151,936.
Data: `results/5090/process_profile.csv` (whole step), `results/5090/process_report.csv`
(per process), `results/5090/results.csv` (end to end). Reproduce with
`./run_local.sh python results/process_report.py --machine 5090`.

## 1. End to end (harness, `unsloth-combined` batch)

| | base Soup | `unsloth` branch | change |
|---|---|---|---|
| whole `soup train` | 14.58 s | 13.22 s | **1.103x faster** |
| training loop, 64 steps | 8.86 s | 7.45 s | 1.19x |
| median step | 115 ms | 88 ms | 1.31x |
| GPU time per step (profiler) | 103.3 ms | 67.1 ms | **−35%** |
| peak GPU memory (nvidia-smi) | 15,763 MiB | 8,320 MiB | **1.895x less** |
| torch max allocated | 13,340 MiB | 6,502 MiB | −6,838 MiB |
| eval loss | 2.05316 | 2.05308 | −0.004% |

Kept for backward, summed over the processes above: **base 9,495 MiB → ours 4,982 MiB
(−4,513 MiB)**. The largest single transient also shrinks, from 4,601 to 1,077 MiB in the
loss. Together these explain the measured −6,838 MiB of torch peak.

### What each optimization bought

| process | time | memory | how |
|---|---|---|---|
| lm_head + CE + metrics | **3.2x faster** (32.3 → 10.2 ms) | peak **−3,524 MiB**, saved −593 MiB | one Triton pass gives lse, loss, entropy and argmax. The grad is written over the bf16 logits, so no fp32 logits are made (base kept up to four fp32 [B,T,V] copies). Metrics reach TRL and Soup through Soup's no-logits protocol |
| MLP | **1.39x faster** (76.0 → 54.8 ms/step) | saved **−3,920 MiB** (5,880 → 1,960) | x is cast once to the 4-bit linear's compute dtype, so gate, up and act are saved in bf16, not fp32. The products are the same, because bnb rounds x to bf16 anyway |
| NF4 dequant | 1.23x faster (9.1 → 7.4 ms/step) | 0 | nested absmax decode and NF4 lookup in one kernel, bit-exact with bnb |
| RMSNorm | about the same per call (launch-bound) | peak −48 MiB/call | 1 launch fwd + 1 bwd instead of about 5+5. In the whole-step profile, element-wise and reduction time fall sharply |
| RoPE | about the same per call (launch-bound) | peak −22 MiB/call | 1 launch instead of about 10. HF saved only cos/sin too, so nothing is saved for backward |
| attention, q/k/v/o projections | unchanged | unchanged | not touched (next candidates, below) |

How to read the isolated ms: each call is timed with CUDA events from the host, so for small
ops (RMSNorm, RoPE) the number is mostly launch/Python overhead, not GPU work. The GPU-side
saving for those shows in section 2 (element-wise −18 ms, reduction −1.2 ms). Isolated calls
also run without the rest of the step, so their per-step sum is not the step time.

## 4. For comparison: real Unsloth on the same task (branch `unsloth-unblocked`)

Measured by the harness with the Unsloth block removed from the solution side only. The
solution loads through Unsloth's `FastLanguageModel` with the same LoRA (q/v, r=16,
dropout 0.05, no checkpointing), and base and solution both ran in Unsloth's venv.

| | base | real Unsloth | ours (`unsloth` branch) |
|---|---|---|---|
| whole command | 15.08 s | 15.64 s (0.964x) | 13.22 s (1.103x) |
| training loop / median step | 8.99 s / 118 ms | **5.15 s / 49 ms** | 7.45 s / 88 ms |
| GPU time per step | 103 ms | **36.5 ms** | 67.1 ms |
| peak GPU memory | 15,727 MiB | **7,623 MiB** (2.06x) | 8,320 MiB (1.90x) |
| eval loss vs base | — | +0.569% | −0.004% |
| challenge checks | — | fails 2, 5, 6, 7, 9 | passes all but 9 (not a T4) |

Unsloth's GPU profile per step: matmul 28.0 ms, NF4 dequant 2.1 ms (its own Triton kernel),
attention 2.0 ms (**flash** kernel, since its padding handling avoids the mask), element-wise
2.3 ms, cast 0.7 ms.

Why it's faster in the loop:
- **Flash attention:** 2 ms vs 8.8 ms.
- **Fewer matmul ms:** 28 vs 45. It loads cut_cross_entropy and fuses the LoRA matmuls. That
  CCE skips the head matmul on unlabelled positions is my reading, not something I measured.
- **No TRL entropy or accuracy at all:** this is why check 5 fails.

Why it's slower overall: importing and patching Unsloth adds about 10 s of startup. It also
changes the outputs. First-step loss is +46% (Unsloth reports the loss differently), and eval
loss is +0.57%, above the 0.5% limit. It also loads a banned library and changes the
allocator settings.

## 5. Where the remaining time and memory are (next steps)

- **Matmul, 45 ms (67% of our step):**
  - Skip the lm_head and its CE work on unlabelled rows. About a third of tokens are prompt,
    so this is about −4 ms, and it is what Unsloth does. Entropy is needed on every row, so
    keep a cheap entropy-only pass for those rows.
  - Fuse the LoRA A/B matmuls into the base GEMM output, as Unsloth's `matmul_lora` does.
- **Attention, 8.8 ms:** passing `is_causal` instead of the padding mask (right padding) would
  use the flash kernel. Unsloth reaches 2 ms; a microbenchmark gave 169 µs vs 254–578 µs per
  layer.
- **Memory, about 4,982 MiB still kept for backward:**
  - MLP bf16 activations: 1,960 MiB. Recomputing gate/up in backward would cost about +12–25%
    time.
  - lm_head: 1,039 MiB, of which about 445 MiB is autocast's bf16 copy of the tied fp32 head.
    Chunking the head matmul would avoid both.
  - SDPA: 731 MiB. Without the mask, repeat_kv is gone, which saves about 280 MiB.

## Limits of this report

- One profiled run per side on a 5090 in bf16. On the T4 (fp16, about 5x slower memory
  bandwidth) the element-wise and CE savings matter relatively more.
- The isolated per-process numbers use random activations of the real shapes on the real
  4-bit layer 0. The values don't matter for time and memory, but section 3 is a model of one
  step, not a trace of the real one. The whole-step numbers in sections 1–2 are from real
  training.
- "saved MiB" counts distinct non-parameter storages that autograd saves. A tensor that is
  also kept alive for another reason, such as the residual stream, still counts once.
